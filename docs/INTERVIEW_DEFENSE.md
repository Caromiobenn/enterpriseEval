# 用本次实验回答面试追问

## 90 秒介绍

我做的是纯文本基础模型的评测方法原型，关注评测版本变化后，哪些结果仍可比较、哪些执行产物可以复用。先实现离职交接和发票核对两个可控工具环境，用状态判分保护无关记录，并注入写入已提交但响应丢失的故障。在双 4090 上对两个 Qwen2.5 AWQ 模型运行冻结矩阵，保存完整工具轨迹和终态。

最具体的发现是：更严格的 grader 也可能误判。旧规则把操作数量固定为参考解长度，导致业务终态正确但多一次无害关联的轨迹失败。我保留原分数，新增私有判分修订，将正确性和冗余分开，再用新参数运行验证。同时真实执行保存产物重判和完整重跑对照，分别记录 token 与 CPU 成本。当前只有两个合成业务家族，不能声称通用长程能力或跨域模型排名；下一步是冻结官方纯文本子域、增加独立任务根和人工复核。

## 为什么这属于基础模型评测，而不是业务应用开发？

业务环境是测量工具。研究变量是模型、调用协议、任务条件及 grader；产出是判分有效性、失败证据、运行可靠性和评测成本。没有开发企业上线应用，也没有把人工编排的流程当模型能力提升。

## 为什么换 grader 可以不重跑？

在本实验中，轨迹先由固定模型、环境、提示与采样条件产生，grader 只在结束后读取产物。修改这个私有函数不会影响已经发生的执行，所以只要产物包含新判分需要的信息，就能重新计算。若 grader 反馈参与规划、反思、搜索或训练，轨迹分布也可能变化，不能直接复用旧轨迹代替新执行。

## 哈希相同就一定能复用吗？

不能。哈希用于检查已记录的内容有没有变化，不能补救遗漏的条件。还要检查产物是否完整、新规则是否需要缺失信息、环境是否可恢复、模型/分词器与运行配置是否冻结。当前是可重放内存环境；生产 API 的时间、权限、数据版本和软件依赖还需要额外建模。采样 seed 单独核对；相同 seed 也不一般性保证所有推理系统逐位确定。

## 你是不是为了让分数好看才放宽 grader？

修订确实发生在看过主集之后，所以明确标为探索性，保留旧标签和源码。修改针对具体合同问题：一次对初始已正确关联记录的无害操作不等于错误退款。必要操作缺失、重复已提交操作、错误退款和保护记录变化仍判失败。再用构造反例及新参数运行检查；这仍不是独立专家验证或新业务家族上的结论。

## 为什么不直接比较模型说“完成了”没有？

轨迹中两个模型都出现过未完成却宣称完成。完成措辞是模型输出，真实状态是被测结果。例子包括错误退款后仍声称核对正确，以及大量请求标识冲突后仍声称离职交接结束。

## 64 次是否足以做统计显著性？

64 是运行单元数量，只有两个语义家族。金额、实体 ID、规模和重复共享结构，不能当 64 个独立业务任务做跨域推断。目前报告按条件计数、配对差异与缺失审计。要估计跨域不确定性，需要更多独立任务根，并按任务根而不是单次运行处理相关性。

## 规模扩展是不是 long-horizon benchmark？

不是。规模 8 同时增加文本、记录和操作数；一次小规模开发集通过也不证明能力已经饱和。这里验证的是保留锚点、另存挑战集合、保证参考解预算可达以及任务变化必须重跑的工程流程。真正的长程评测还要定义规划深度、反馈延迟、可恢复性等维度，并分离上下文长度与工具步骤数的影响。

## 你复现了哪些论文？

没有声称完整复现 AppWorld、τ-bench、AgentBoard 或 tinyBenchmarks。采用了已核验的一手工作中的状态判分、多步诊断、动态挑战及评测经济性思想，在现有硬件上实现了受控小实验。论文出处、会议记录、影响证据和未复现部分均在 FOUNDATIONS 中明确列出。

## 经济性结果有什么限制？

相同产物的私有重判可以没有额外推理，这是结构性条件，不是学出来的压缩算法。完整重跑对照提供实际 token 成本，但不能把累计 GPU episode 秒数除以一个 CPU 判分内核时间，包装为普适加速比。还应报告读取、验证、重放与存储开销，以及不能复用的变化比例。

## 接下来 20 天最有价值的工作是什么？

先把这次所有主张演示清楚：从原始轨迹定位一个模型错误、一个 grader 问题和一个迁移决策。随后接入冻结官方版本的纯文本子域，增加独立任务根，对判分做人工盲审，再考虑低成本子集与不确定性。暂不增加多模态、新训练系统或未经验证的自动任务演化机制。
