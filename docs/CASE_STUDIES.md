# 可在面试中逐条展示的失败与判分案例

这些是主矩阵中的真实模型记录，已逐步重放工具事件。描述是轨迹观察，不是对模型内部原因的证明。

## 1. Grader 把多余操作误当结果错误

[7B 原始记录 37fd0863a0bd34e116a3](../artifacts/v2-main/results/37fd0863a0bd34e116a3.json)：发票核对、规模 2、故障开启。模型关联了必须关联的 payment-69294-2，又关联了原本已正确关联的 payment-69294-1。后者没有改变业务状态。随后退款、关闭两张发票，完整终态正确。

历史 v1 要求恰好 4 个成功写操作，观察到 5 个，因而判失败；v2-outcome 接受业务结果，记录 1 次无害冗余。该轨迹没有重复同一个已提交操作。不能把它与重复退款导致现金错误混在一起。

面试重点：独立 grader 也需要验证；“更多约束”不是“更准确”的同义词。原先人工构造测试只覆盖两个参考执行顺序，没有覆盖额外无害操作，测试全部通过仍可能过拟合参考解。修订后保留旧分数，并在新参数集验证。

## 2. 只看目标标志会漏掉错误退款

[7B 原始记录 b4285fab1f6628e3e62f](../artifacts/v2-main/results/b4285fab1f6628e3e62f.json)：发票核对、规模 4、无注入故障。模型除退回两笔重复支付外，还退回了不应退的 payment-28398-5。该发票此前已被关闭，因此“所有发票关闭”的旧 v0 检查通过，但现金和支付终态错误；实际现金变为 4600。

模型最终声称核对完成，不能取代独立状态验证。v1 与修订后的 v2-outcome 都拒绝该结果。v0 是本项目刻意不完整的检查器，这个例子不能表述成发现了 AppWorld 或 τ-bench 漏洞。

面试重点：要同时检查正向目标与附带影响；执行期间的检查和结束后的状态检查可能各有盲区。业务工具允许某操作，不代表它符合当前任务。

## 3. 请求标识复用错误与“口头成功”

[7B 原始记录 2b4186d8db0c119e73b1](../artifacts/v2-main/results/2b4186d8db0c119e73b1.json)：离职交接、规模 4、故障开启。轨迹中有 21 次“request_id belongs to a different operation”错误；实际只完成一次资产转交和三次权限回收，账号没有按要求停用。模型仍输出全部完成。

提示已要求不同操作使用不同 request_id；这条轨迹说明该具体模型运行没有持续遵守协议。它不能单独证明模型缺少某个抽象认知能力，也不能把所有失败归因为故障注入。应结合 clean/fault 配对条件及提示对照检查。

面试重点：幂等键是“一项操作”的身份，不是“整个任务”的身份；同操作超时可用相同键重试，不同操作复用该键会冲突。`actor_finished` 与 `task_success` 必须分开。

## 4. 14B 也会在未完成状态下结束

[14B 原始记录 0e079bb9f129f3939c5e](../artifacts/v2-main/results/0e079bb9f129f3939c5e.json)：发票核对、规模 4、无故障。模型错误退回 payment-28398-5，并遗漏了它应有的关联；最后一张发票无法关闭。模型识别到付款总额不匹配，却据此宣称不需进一步操作并结束。

面试重点：较大模型在这批条件中总分更高，不等于所有子条件都可靠；模型对错误的文字解释也不是正确性证据。应从工具前置条件、实际状态和未完成义务建立诊断。

## 能说与不能说

可以说“定位了操作标识冲突、错误退款、未完成即终止和判分过度约束的具体轨迹”。不能把观察直接包装成因果归因；下一步需要针对某个假设做控制干预，并在未用于修订的业务家族上复核。
